# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`api-lib` is a **boilerplate/template** for spinning up new API backends — not a finished product. It provides a batteries-included Bun + Hono server with multi-provider authentication, session storage, and auto-generated CRUD routes over a Prisma schema. New projects are meant to start from this repo and build on top of it by editing `api.ts` and `prisma/schema.prisma`.

## Commands

- Install deps: `bun install`
- Run the server (dev/prod, no build step — Bun runs TS directly): `bun run index.ts` or `bun start`
- Generate the Prisma client after editing the schema: `bunx prisma generate` (output is written to `tools/generated/prisma`, matching the `generator client { output = ... }` in `prisma/schema.prisma`)
- Push schema changes to the database: **use `bunx prisma db push`, not `prisma migrate`** — this template doesn't use migration files, so always push the schema directly.
- Run via Docker (app + Postgres + Redis): `docker-compose up --build`
- Count lines of code per file: `bun run tools/count-lines.ts`
- Create a new local user (priv 1 = admin): call `POST /newuser` as an authenticated admin (see `tools/auth.ts`), or hand-edit `auth.json`
- Run an ad-hoc SQL file against `DATABASE_URL`: `bun run-sql.ts <file.sql>` (add `--json` for JSON output instead of a table). Use this to look at actual data — real rows, real shapes, real edge cases — before building a new feature or CRUD route against a model, rather than guessing from the schema alone.

There is no lint config, no test runner, and no build step configured in this repo — don't invent commands for these.

Runtime introspection: once the server is running, `GET /endpoints/html` (or `/endpoints/json`) lists every registered route. Check this first when you need to know what's actually mounted — it reflects the real registration order (including anything auto-generated by `exposePrismaCRUD`) rather than what you'd infer from reading `api.ts` alone. Try it against `http://localhost:<PORT>/endpoints/json` for local work; if the project has a known production URL, hit `<production-url>/endpoints/json` too so you're working from what's actually deployed, not just what's in the working tree.

## Architecture

**Entry point wiring (`index.ts`)** assembles the app in a specific, order-dependent sequence:
1. `expose(app)` from `tools/listEndpoints.ts` — adds the introspection routes.
2. Static file serving from `./public`.
3. `authPublic(app)` and `API.publicRoutes(app)` — routes reachable without a session.
4. `authMiddleware(app)` — a catch-all `app.use("*", ...)` that gates **everything registered after it**.
5. `authPrivate(app)` and `API.privateRoutes(app)` — routes that require a valid session.

Because Hono matches middleware/routes in registration order, anything added after step 4 requires auth by default. Public/private route separation in `api.ts` mirrors this — new endpoints go in `publicRoutes()` or `privateRoutes()` accordingly.

**`api.ts` is the project-specific layer.** It's the file a new project built from this template is expected to edit — everything under `tools/` is meant to stay generic/reusable. `api.ts` also wires an `onLogin` callback and calls `exposePrismaCRUD("api", app)` to mount the generated CRUD routes.

**Auth (`tools/auth.ts`)** supports four login paths that all converge on the same `Session` object and cookie-based `auth_token`:
- Local username/password (md5-hashed, stored in `auth.json` — a flat JSON file, not a database table).
- Google OAuth (redirect flow, or one-click credential verification via `/auth/google-oneclick`).
- Microsoft OAuth (redirect flow via Microsoft Graph).
- CAS (delegates to an external CAS server when `CAS_SERVER_URL`/`CAS_CLIENT_ID` are set — Google/Microsoft routes redirect to the CAS server instead of handling OAuth locally when CAS is configured).

Sessions are stored via a pluggable `SessionStore` (`MemoryStore` by default, `RedisStore` via `setSessionStore("redis")` in `index.ts`, backed by `REDIS_URL`). `auth.json` persists user records (password hash, privilege level, current session token) across restarts; it's gitignored and treated as a dev-only user store, not a production user database.

**Auto CRUD (`tools/prisma.ts` + `tools/createCRUD.ts`)**: `exposePrismaCRUD` reads every model off the generated `PrismaClient`, parses `prisma/schema.prisma` directly (via regex, in `parseSchema()`) to determine each model's primary key and foreign keys, and mounts a full REST CRUD surface per model at `/<prefix>/<model>` (list, get by id, paginated list, filter/query, create, update, delete), plus `/<prefix>/_schema` exposing the parsed schema. `createCRUD` accepts optional `checkPermissions` and `validateData` callbacks per-route for authorization and row-level filtering (`PermissionResult.rowLevelFilter` is merged into `where` clauses and enforced on writes) — this is the hook point for adding access control without touching the CRUD generator itself.

The Prisma datasource adapter (`pg` vs `mariadb`) is selected at runtime in `tools/prisma.ts` based on the scheme of `DATABASE_URL` (`postgres(ql)://`, `mysql://`/`mariadb://`).

**`run-sql.ts`** (repo root) runs an arbitrary SQL file against `DATABASE_URL` via Bun's built-in `SQL` client and prints the results as a table (or JSON with `--json`). It's the quickest way to inspect real data — reach for it before/while building a feature against a model, instead of relying solely on `prisma/schema.prisma` to infer shapes.

**Supporting tools (`tools/`)**:
- `fileUpload.ts` — multipart upload handler, writes to `./uploads` (gitignored).
- `mail.ts` — sends email via Gmail SMTP (nodemailer) or Linux `sendmail`, chosen by `EMAIL_TYPE` env var.
- `googleapi/google.ts` — Google Workspace API helpers (Drive, Apps Script) using a separate desktop-app OAuth flow (`tools/googleapi/credentials.json` + `token.json`, both gitignored) — unrelated to the end-user login flow in `tools/auth.ts`.

**`public/`** is a minimal demo frontend: `index.html` + `api.js` (fetch wrappers for the auth/CRUD endpoints) plus a small library of dependency-free vanilla-JS UI components (`combobox-input.js`, `date-range.js`, `file-drop.js`, `map-picker.js`, `rich-text.js`, `star-rating.js`, `tag-input.js`), demonstrated in `components/demo.html`. This is a reference/demo, not a framework — new frontends aren't required to use it.

**Deployment**: `Dockerfile` is a multi-stage Bun build (installs deps, runs `prisma generate` against a placeholder `DATABASE_URL` at build time, then copies into a slim runner image). `docker-compose.yml` runs the app alongside Postgres and Redis containers for local/prod-like use. `entrypoint.sh` is the container's start command.

## Environment variables

Copy `example-env` to `.env`. Key variables: `DATABASE_URL` (postgres/mysql/mariadb, required), `PORT`, `REDIS_URL` (if using the Redis session store), `CAS_SERVER_URL`/`CAS_CLIENT_ID`/`CAS_CALLBACK_URL`, `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/`GOOGLE_REDIRECT_URI`, `MS_CLIENT_ID`/`MS_CLIENT_SECRET`/`MS_REDIRECT_URI`, `GMAIL_USER`/`GMAIL_PASS`/`EMAIL_FROM`/`EMAIL_TYPE`. Routes for a given provider return a `503` with a "missing env vars" hint if that provider isn't configured, rather than failing silently.

## Family Registry domain details

This project is the Postgres/Prisma successor to `prototype/` (the original MySQL + Express family-tree app — see `prototype/CLAUDE.md` for its full permission-resolution algorithm, which this section assumes as background).

**Auth**: uses CAS delegation (`setupPublicRoutes`'s `/auth/google` and `/auth/microsoft` both redirect to `CAS_SERVER_URL` when it's configured, which it is here) rather than direct Google OAuth — `session.email` is populated the same way regardless of which provider path was used (Google/Microsoft/CAS/local), so `family.ts` and `api.ts` only ever read `session.email`, never a provider-specific field.

**Schema (`prisma/schema.prisma`)** — three models instead of the prototype's five tables:
- `Person` (`people` table) — same fields as the prototype's `people`, plus a real Prisma relation `familyId -> Family.familyId` (the prototype had no DB-level FK here). `fatherId`/`motherId`/`spouseId` stay as plain unenforced `Int?` columns, matching the prototype — genealogy data is routinely incomplete, and a hard self-referential FK would reject legitimate partial records.
- `Family` (`family` table) — one row per family tree, merging the prototype's `roots` (root ancestor pair → `fatherId`/`motherId`), `owned_families` (→ `owner`, nullable — some legacy root rows had no owner) and `family_permissions` (→ `permissions`, a JSON array of `{ email, role }`) into a single entity, since all three were small, family-scoped data.
- `User` (`users` table) — renamed from the prototype's `security`; same `email`/`role`/`logins` shape.
- The prototype's `family` table (an `(id, family_id, owner)` table, unrelated to and unused alongside `owned_families`) was dropped — dead scaffolding, never referenced in `prototype/api.js`.

**Data migration (`tools/migrate-from-mysql.ts`)**: one-time script, run once against a MySQL instance loaded with the old dump (`family_db_jul_2026.sql`) and the target `DATABASE_URL`. It wipes and re-populates `person`/`family`/`user`, preserving original `Person.id` values (so `fatherId`/`motherId`/`spouseId` cross-references stay valid) and resetting the Postgres sequence afterward. One old `roots` row (`family_id = "Nathan Southwick"`) is deliberately skipped as an orphaned duplicate — no owner, no people tagged with that family_id, and its root ancestors are the same two people already covered by the `sagers` family's root row under a different name.

**Custom routes (`api.ts` + `family.ts`)**: `family.ts` ports the prototype's `getFamilyIds`/`getVisiblePeopleIds`/`getFamilyPermissions`/`canEditFamily`/`getDescendantsWithGenerations` onto Prisma queries against the merged schema — no raw SQL, no session-side caching (recomputed per request; tree sizes here are small enough that this is simpler than threading cache invalidation through `tools/auth.ts`, which is meant to stay generic). `api.ts` wires these into the same route surface as the prototype (`/people`, `/people/:name`, `/descendants/:personId`, `/family/:id`, `/roots/:familyId`, `/family-permissions/...`, etc.), plus the generic CRUD routes from `exposePrismaCRUD`.

**Generic CRUD lockdown**: `checkCrudPermissions` in `api.ts` is passed to `exposePrismaCRUD` and dispatches on the model name parsed out of the action string (`"GET:api/person"` → `"person"`). `person` reads are row-filtered to the caller's visible-people set; writes require `canEditFamily`. `family` reads are filtered to families the caller has any permission on; creates force `owner` to the caller's own email (ignoring any client-supplied value); updates/deletes require the caller to be the row's `owner`. `user` is blocked entirely (`{ allowed: false}` unconditionally) — the prototype never exposed `security` via raw CRUD either.

**Fixes made vs. the prototype** (flagged during migration, not present in the original):
- `GET /people` now returns a plain JSON array of objects instead of the prototype's CSV-shaped array-of-arrays (`db.queryToCSV`) — see the "Data shape gotcha" note in `prototype/CLAUDE.md` for what this replaces.
- The free-form field list clients can set via `POST /people`/`POST /people/:name` (`family.ts`'s `PERSON_FIELD_MAP`) excludes `family_id`/`id` — the prototype let any submitted column through, which meant a user with edit access to one family could silently move a person into a different `family_id` without that family's permission being checked.
- The prototype's local username/password login path hardcoded `google_data.email = "nathansouthwick@gmail.com"` for every non-OAuth login (`prototype/index.js`) — almost certainly a debugging leftover. This isn't carried forward; a session without a real `email` (i.e. local login) now gets a `400` from any route that needs one, rather than silently acting as that hardcoded account.

**Known gap**: the CAS login flow itself (redirect to `CAS_SERVER_URL`, token verification against it) hasn't been exercised end-to-end in this environment — that server is external and not reachable from here. Everything downstream of a valid session (route logic, permissions, CRUD) was verified by forging a session directly into the Redis session store during development.

## Frontend (`frontend/`)

Flutter, chosen so the same codebase can later target Android/iOS (Flutter for mobile) in addition to the web/PWA build shipped now. Structure:

- `lib/core/api_client.dart` — thin JSON `http` wrapper. Defaults `baseUrl` to `''` (relative paths) — the supported deployment is this app served same-origin from the backend's `public/`, so the browser sends the session cookie automatically with zero CORS configuration. `--dart-define=API_BASE_URL=...` exists only for standalone `flutter run -d chrome` iteration against a backend on a different port, which additionally needs CORS + credentials enabled server-side (not done, since it's not the supported path).
- `lib/core/auth_state.dart` — a `ChangeNotifier` holding `/user` + `/permissions`, recomputed on `refresh()` (called once at startup, and by `settings_screen.dart` after creating a family) rather than patched in place.
- `lib/core/csv_export/` — conditional-import split (`dart.library.html`) so `browse_screen.dart`'s CSV download compiles on all three target platforms; it's a no-op on non-web builds (the button is hidden there via `kIsWeb`).
- `lib/screens/` — one file per screen (see README for the list), wired up by `lib/app.dart`'s `go_router` config. `AppShell` (`screens/app_shell.dart`) is the shared nav chrome, adaptive between a `NavigationRail` (≥800px) and a bottom `NavigationBar`.
- Auth gating happens in `GoRouter`'s top-level `redirect`, driven by `AuthState` via `refreshListenable` — no per-screen auth checks needed.

**Tree screen** (`lib/tree/`): a pannable/zoomable canvas, ported from the prototype's `tree.js`, not the simpler person-picker + list it started as. `lib/tree/tree_layout.dart` is a faithful line-by-line port of `tree.js`'s `buildLayout()` — same three passes (top-down sort to fix sibling order → bottom-up placement centering parents over children → childless-spouse tuck-in) and the same layout constants, operating on `TreeNode`s built from `GET /descendants/:personId` (a per-render generation label, e.g. `"2.1"` for a spouse — distinct from `Person.generation`, which this ignores, matching the prototype). Two differences from a literal port, both wins from being in Flutter rather than `<canvas>`:
- Nodes are real widgets (`lib/tree/tree_node_widget.dart`) positioned in a `Stack` via the layout's `(x, y)`, not `canvas.fillText`/`roundRect` calls — so hit-testing (tap to re-root the tree on that person) is just a `GestureDetector`, and text stays crisp at any zoom level with no manual measure-and-truncate loop.
- Pan/zoom is `InteractiveViewer` (`trackpadScrollCausesScale: true` so wheel/trackpad scaling matches the prototype's wheel-to-zoom) instead of hand-rolled pointer/touch math — connector lines (`lib/tree/tree_painter.dart`, a `CustomPainter`) sit in the same coordinate space, positioned behind the nodes in the `Stack`.

Verified interactively (see below): multi-generation rendering, gender-based node coloring, spouse/parent-child connector lines, zoom, and tap-to-re-root all confirmed against real migrated data (the `sagers` family, 5 generations deep).

**Calendar screen** is a month grid, ported from the prototype's `populateCalendarMonth()` (`main.js`): birthdays recur every year, so it cycles a bare 0–11 month index rather than a real year/month pair — a person matches "this day of this month" in whichever year is currently displayed, same as the prototype. Deliberately does **not** filter out people with a `deathDate` (matching the prototype) — a deceased person's birthday still shows, just in a muted chip color as a visual-only distinction the prototype didn't have. Tapping a name navigates to `/person/:name`, same as the prototype's `handleClick`.

**Prototype parity pass** (see `TODO.md` for the full tracked list): closed the gaps found when comparing against the prototype's `main.js` in full.
- `lib/widgets/person_picker.dart` — a shared live-search picker (type a name, tap a match), replacing free-text relationship fields. Used by Profile (father/mother/spouse/children), Settings (setting a family's root ancestors — `POST /roots/:familyId` existed server-side but had no UI before this), and Browse (the "descendants of" filter).
- `lib/browse/tree_order.dart` — a faithful port of the prototype's `computeTreeOrder` (root → spouse → children, birth order, recursive). Browse now filters by gender/status/age-range/has-birthday/descendants-of and sorts by this depth-first order by default, matching what the prototype's own README called "sortable by a computed depth-first family order."
- Tree screen's person list and Settings' family cards gained the same live-filter/role-badge treatment as other screens.

**Flutter web gotchas hit during this pass** (both caused real runtime crashes, not just lint noise — worth remembering before writing similar code):
- `DropdownButtonFormField<T>` must be instantiated with a **non-nullable** `T`. Passing a nullable type as `T` itself (e.g. `DropdownButtonFormField<String?>` because the selected value is `String?`) compiles fine but throws a `TypeError` deep in Flutter's internals the moment the dropdown opens. The fix: keep `T` non-nullable, let `value`/`onChanged` be `T?` via the framework's own optional handling, and add an explicit `DropdownMenuItem<T>(value: null, ...)` for the "All" option. See `lib/screens/browse_screen.dart`'s `_dropdown` helper.
- `Spacer` only works inside `Flex`/`Row`/`Column` — putting one inside a `Wrap` (e.g. to push a trailing action to the end of a wrapping filter bar) throws a `ParentDataWidget` assertion at runtime. Both of these were caught by rebuilding with `flutter build web --debug` (unminified, real stack traces) rather than trying to decode the minified release-build error — that's the move when a release build throws an opaque `type 'minified:X' is not a subtype of minified:Y` error.
- `ConstrainedBox(maxWidth: N)` as a direct child of `SingleChildScrollView` does **not** limit width on its own — the scroll view gives its child a *tight* cross-axis constraint (matching the full viewport), which wins over a bare `maxWidth`. Needs `Center(child: ConstrainedBox(...))` (or `Align`) to actually get a narrower, centered reading column. Fixed in `profile_screen.dart`.

**Verification performed**: `flutter analyze` is clean; `flutter build web` succeeds. Since there's no real CAS server reachable here, end-to-end browser verification used the same Redis session-forging technique as the backend (see above) plus a headless Playwright run (`context.addCookies` with the forged `auth_token`) — confirmed all screens render with real migrated data (family-scoped visibility, resolved relationship names, correct permission-gated edit affordances) and zero browser console errors, including the interactive flows added in the parity pass (root-setting, Browse filter combinations, add-spouse-and-save). Flutter web renders to `<canvas>` (CanvasKit), so it has no queryable DOM text nodes — don't reach for `page.getByText(...)`-style selectors when re-verifying; screenshot and/or coordinate-based interaction is the working pattern here. `flutter build web --debug` (same static output shape, unminified) is the move when a release build throws an opaque error and you need a real stack trace.

**Deploying the frontend build**: not yet wired into the Dockerfile/CI — `./build-frontend.sh` is a manual step (`flutter build web` + copy into `public/`) because the production Docker image only has Bun, not the Flutter SDK. A real pipeline would add a `flutter build web` stage to the Dockerfile (or build it in CI and ship the static output), which needs the Flutter SDK available in that build environment — out of scope for this first pass.

## Mobile auth: native Google sign-in, not CAS

Web keeps using CAS (see above) unchanged. Mobile skips CAS entirely and uses direct Google sign-in instead — decided this way because CAS's cookie-based session has no equivalent on a native app (no browser cookie jar), while Google sign-in is a well-supported first-party Flutter flow that reuses backend support that already existed.

- **Backend** (`tools/auth.ts`): `/auth/google-oneclick` already verified a client-supplied Google ID token against `GOOGLE_CLIENT_ID`, and its session middleware already accepted a plain token via the `authorization` header as a fallback to the cookie — both were built generically, so mobile needed zero new backend routes. The one change: both `/auth`'s and `/auth/google-oneclick`'s success responses now also return `token` in the JSON body (previously cookie-only), since that's what a mobile client without a cookie jar needs to capture and reuse.
- **`GOOGLE_CLIENT_ID`** (`.env`/`example-env`) is set to the prototype's original Google Cloud "Web application" OAuth client (`1016767921529-...apps.googleusercontent.com`) — reused rather than creating a new one, per the user's direction. This value is also hardcoded as `serverClientId` in `frontend/lib/core/auth_state.dart`; the two must always match, since that's what makes the ID token `google_sign_in` returns on mobile verifiable by this same backend.
- **Flutter side**: `lib/core/token_store.dart` (secure on-device storage for the session token, via `flutter_secure_storage`), `AuthState.signInWithGoogleMobile()` (runs the native Google sign-in, posts the ID token to `/auth/google-oneclick`, stores the returned token), `AuthState.restoreMobileSession()` (called once at startup on mobile — see `app.dart`'s `_init()` — so the app doesn't look logged-out on every cold start), and `ApiClient.setToken()` (attaches the stored token as a plain `authorization` header on every request; a no-op on web, which never calls it). `login_screen.dart` branches on `kIsWeb` to show the right button/flow.
- `GoogleSignIn` is constructed lazily (`AuthState._googleSignIn` getter, not a field initializer) and only ever touched on mobile — constructing it unconditionally also initializes google_sign_in's *web* plugin (which tries to load Google's JS SDK), which web never needs since it goes through CAS, and which threw a real (if harmless-looking) `pageerror` in testing before this was made lazy.
- **Still needed before mobile Google sign-in actually works, and requires the user's own Google Cloud Console access** (not something this environment can do): register an **Android** OAuth client under the same Google Cloud project, keyed to package name `com.msouthwick.family` + the signing certificate's SHA-1 (debug keystore SHA-1 for local testing: `3B:9B:C2:2D:7A:0E:FD:28:B7:2E:65:5D:F6:EA:A6:9F:69:6F:AB:96` — a *release* keystore will need its own SHA-1 registered too, later); and an **iOS** OAuth client keyed to bundle ID `com.msouthwick.familyRegistry`, whose reversed-client-ID needs adding to `ios/Runner/Info.plist` as a URL scheme (standard `google_sign_in` iOS setup) once that client exists.
- Android `applicationId`/`namespace` is `com.msouthwick.family` (renamed from the `flutter create` default `com.msouthwick.family_registry` per user request — `android/app/build.gradle.kts` and the `MainActivity.kt` package/path were both updated). iOS bundle ID is still the scaffold default (`com.msouthwick.familyRegistry`) — not renamed, wasn't asked for.

## Planned: sync selected people to phone contacts (mobile-only)

Assessed as feasible, not yet built — depends on the Flutter *mobile* build existing (no browser API can write to a phone's native address book, so this can't happen in the PWA).

- **One-way export only** (app → phone), not continuous two-way sync. This data is a shared, multi-editor family tree; letting the OS Contacts app write back would mean resolving conflicts across every family member's device for little real benefit. "Push selected people to my phone's address book" is the actual use case and is much simpler.
- **Package**: `flutter_contacts` — standard, actively-maintained, handles create/update/delete of native contacts on both iOS and Android through one API. Verify current maintenance status when actually implementing.
- **Permissions**: Android `READ_CONTACTS`/`WRITE_CONTACTS`, iOS `NSContactsUsageDescription` — both standard runtime-permission dialogs. Request only when the user taps "sync," not on app launch (matters for App Store review, since contacts access gets extra scrutiny).
- **UI**: multi-select on Search or Browse (checkboxes + "Add N to Contacts"), reusing the visibility scoping the backend already enforces — you can only sync people you can already see.
- **Field mapping** is direct: name, phone, email, address map to their native equivalents; birthday maps to the OS's native birthday field, which gets synced people real iOS/Android birthday reminders for free. `Person.photo` is currently just a filename string with no image-serving wired up — contact photos need that built first; everything else works with what exists today.
- **Avoiding duplicates on re-sync**: store a local (on-device) `person_id → native_contact_id` mapping so re-running the sync updates existing contacts instead of duplicating them. Native contact IDs aren't shareable across devices, so this mapping is inherently per-device — that's fine for what the feature needs.
- **Rough effort**: a few solid days once the mobile app exists — permission flow, multi-select UI, create/update logic, and real-device testing (contacts APIs have iOS/Android quirks that mostly only show up on physical hardware, not simulators).
